# AI Search 容量限流调优方案

## 1. 实测现状

2026-09-14 02:14 UTC 手动触发 `ai-search-sync.yml`（Run `34798545489`）后，
索引统计与查询抽样结果如下。

| 指标 | 2026-09-13 06:17 UTC | 2026-09-14 02:14 UTC |
| --- | --- | --- |
| 队列 | 0 | 0 |
| 进行中 | 0 | 0 |
| 完成 | 0 | 38 |
| 失败 | 301 | 263 |
| 失败明细 | out_of_capacity 296 / timeout 5 | out_of_capacity 263 |
| 向量数 | 98 | 152 |

查询抽样：

| 查询 | `result_batch.results` |
| --- | --- |
| `Docker 安装 Redis` | 空（三次请求结果一致） |
| `Docker` | 5 条 |
| `Redis` | 2 条 |
| `Nginx` | 非空 |
| `hello` | 非空 |

两种情况并存：索引未建立完成，且已入库部分只覆盖原文档的一小部分。
单例词条可命中，跨主题复合查询落空。

## 2. 归因修正

`cloudflare/README.md` §4 与 `adr/2026-09-11-面向-AI-的检索方案选型.md` §5.1
把 `workers_ai_out_of_capacity_error` 归因于每日 10,000 Neurons 免费额度耗尽。
该归因不成立，需要更正。

Workers AI 有两种不同性质的限制，均返回 HTTP 429，但语义相反：

| 错误码 | 含义 | 是否可重试 | 缓解方式 |
| --- | --- | --- | --- |
| 3036 | Account limited，当日免费额度已用尽 | 重试无效，次日 00:00 UTC 重置 | 控制用量或升级付费 |
| 3040 | Out of capacity，当时无可用 GPU 承接请求 | 瞬时态，重试通常成功 | 错峰、降低并发、提升优先级 |

`workers_ai_out_of_capacity_error` 对应 3040 而非 3036。三条证据：

1. 2026-09-14 触发时点为 02:14 UTC，处于当日额度重置后不久，
   按既有估算单次全量索引仅约 214 Neurons（占每日额度约 2%），不具备耗尽额度的条件；
2. 社区反馈中多个 AI Search 实例在 Dashboard 显示额度已重置为 0 / 10,000 的情况下，
   索引仍返回同一错误，且与 R2 源、文件格式、鉴权、计费均无关；
3. 失败明细中另有 `workers_ai_timeout_error` 与 `timeout_error`，
   与 3040 同属资源侧不可用，而非配额超限。

由此可得：瓶颈是 Workers AI 嵌入侧的瞬时容量与优先级，不是每日免费额度。

## 3. 现有缓解手段为何无效

### 3.1 定时把同步安排在额度重置之后

`.github/workflows/ai-search-sync.yml` 的注释写明「安排在重置之后触发同步，
让索引任务在额度最充裕时执行」。前提是额度为瓶颈。既然瓶颈是瞬时容量，
把任务挪到 01:17 UTC 对 3040 无缓解作用；若该时刻恰好是同批免费用户的集中触发点，
反而提高撞上限的概率。

### 3.2 通过缩小索引规模来降低压力

`sitemap-ai.xml` 已把 URL 由 1492 条收敛到 367 条，向量写入量减少约四倍。
这一项仍然必要，因为它降低了总需求量。但它无法改变单次任务的**瞬时并发**
——AI Search 的索引作业按批推进（社区案例中可见 batch of 100 items），
一批内的请求并发过高时整批失败，与总数多少无关。

### 3.3 分块调优的收益上限有限

按 `dist/raw` 下 367 篇原文统计（合计 493,614 字符，中位数 778 字符，
P75 1,717 字符，最大 12,856 字符），不同分块参数下的估算总块数如下：

| chunk_size | overlap | 估算块数 | 相对基线 |
| --- | --- | --- | --- |
| 1024 | 10% | 611 | 基线（当前配置） |
| 1024 | 0% | 591 | −3% |
| 2048 | 0% | 439 | −28% |
| 4096 | 0% | 381 | −38% |
| 8192 | 0% | 368 | −40% |

由于语料以短文档为主（中位数低于单次分块容量），多数文档本就落在单块内，
因此调大 chunk_size 的理论上限只到「每篇一块」，即最多减少约 40%，
且会把检索粒度放大到整篇，损失片段级定位能力。

在**批量性失败**的场景下，削减 28%–40% 的请求量不足以改变整批被拒的结果。
分块调优可作为辅助项，不作为主攻方向。

### 3.4 自动同步与计划任务叠加

实例配置 `sync_interval: 21600`（6 小时）本身会周期性触发索引作业，
而 GitHub Actions 每日 01:17 UTC 再触发一次。两者职责重叠时，
同一批失败文件会被反复重排。应当明确区分：由实例自身承担周期性增量，
外部工作流只承担「确认收敛」与「按需重排」的职责。

## 4. 核心判断

索引作业受阻于 **Workers AI 免费层在嵌入高峰期的容量优先级**，具体表现为：

- 失败模式为批量而非逐个，同一批文件反复失败；
- 单次触发后被处理的 301 项中仅 38 项完成，向量数 152 / 估算 611 块，覆盖率约 25%；
- 索引覆盖的**完整性**比广度更影响可用性。当前约 25% 的随机稀疏覆盖下，
  任何跨主题查询都可能落空；若改为覆盖 100% 内容的关键词索引，
  单主题查询可全部可用。

因此调优方向应当是**绕开或降低对嵌入产能的依赖**，而非继续压缩内容或调整时点。

## 5. 方案

按「成本由低到高、收益由大到小」排列，层一与层二建议并行推进。

### 5.1 层一：双阶段索引，先把 index_method 切到关键词单路

**思路**：AI Search 支持 `index_method: { keyword, vector }` 分别开关。
关键词索引构建的是 BM25 倒排索引，不经过嵌入模型，因此不消耗嵌入产能，
理论上不受 3040 约束。把索引拆成两个阶段：

| 阶段 | index_method | keyword_tokenizer | 目标 | 能力 |
| --- | --- | --- | --- | --- |
| A | `{keyword: true, vector: false}` | `trigram` | 全站 100% 覆盖 | 子串与关键词匹配，无语义召回 |
| B | `{keyword: true, vector: true}` | `trigram` | 增量补齐向量 | 关键词与语义混合检索 |

阶段 A 先行，使问答具备全站可用性；待产能宽松（或完成 5.5 的付费调整）后再切到阶段 B，
由增量补入向量。切换 `index_method` 会触发全量重索引，但阶段 A 的重索引不依赖嵌入，
因此具备可执行性。

`keyword_tokenizer` 取 `trigram` 而非默认的 `porter`：porter 是词级加 Porter 词干提取，
面向英文自然语言；本站内容以中文技术文档为主，含大量命令、配置项、报错串与标识符，
字符级子串匹配（`trigram`）对此类字面串更直接。该项变更同样会触发全量重索引。

**字段位置**：`keyword_tokenizer` 必须置于 `indexing_options` 内。置于顶层时接口返回
2xx 但静默丢弃，实例回读始终为 `{"keyword_tokenizer": "porter"}`。
该错误在首次实施时未被发现（`context_expansion` 同类，见 §5.6.0），
后果是分词器实际停留在 porter，中文查询全部落空，见 §6.3。

**收益**：零现金成本；解除对嵌入产能的依赖；索引覆盖率由约 25% 提升至接近 100%。
**代价**：失去语义召回，「容器怎么固定 IP」这类不出现关键词的问法仍会落空。
**前置验证**：需先确认 keyword-only 模式下索引作业确实不发出嵌入请求
（以索引期间 Workers AI 用量不增长为准）。

### 5.2 层二：应用层降级检索，用站内既有资产兜底

**思路**：不让 AI Search 独自承担召回职责。站点构建产物中已有三项可直接复用的资产，
且均不经 AI Search：

| 资产 | 规模 | 线上可用性 |
| --- | --- | --- |
| `/raw/**/*.md` 逐篇原文 | 367 个文件 | `200` 实测可达 |
| `/llms.txt` 与 `/_llms-txt/*.txt` 分类路由 | 10 个分卷，12K–272K | `200` 实测可达 |
| `/pagefind/**` 静态索引 | 1,468 fragments，约 8 MB | `200` 实测可达 |

其中 `/raw/**` 与 `/_llms-txt/**` 当前在 AI Search 的 `exclude_items` 中被排除
（理由是与页面正文重复），这是为索引去重服务的正确配置，
但这些资产本身可作为**独立的检索层**供应用使用。

设计一个薄的问答 Worker（可沿用 NLWeb 之外的独立路由），按以下链路工作：

1. 取 `/llms.txt` 的目录作为候选清单，用关键词或分类匹配筛出若干候选主题；
2. 对候选范围内的 `/raw/*.md` 做轻量 BM25 或子串打分，取得 top-K 片段；
3. 把片段交给 Workers AI 生成模型作答，并在响应中附来源 URL。

**收益**：

- 召回阶段零 Neurons（静态文件读取不经 Workers AI），仅生成阶段计费，单次约 60 Neurons；
- 覆盖率恒为 100%，不依赖索引收敛，与 AI Search 的进度解耦；
- 可作为 `/ask` 的降级后端：AI Search 返回空时改走关键词链路，
  使 `Docker 安装 Redis` 这类查询在当前状态下也能得到非空响应。

**代价**：需要开发与维护一段 Worker 代码；`adr/2026-09-11-面向-AI-的检索方案选型.md`
§3 曾以「开发成本」为由排除自建 Worker 方案，当时的前提是 AI Search 能够满足需求，
该前提已被本次实测推翻，因此需要重新评估而非直接沿用旧结论。

### 5.3 层三：数据源换轨为 R2 直喂纯净 Markdown

**思路**：当前数据源是 `web-crawler`，链路为抓取 HTML → 渲染 → Markdown 转换 →
分块 → 嵌入。其中 Markdown 转换由 Workers AI 的 toMarkdown 服务完成，
属于嵌入之外的另一处产能消耗点，这也解释了为何大量 URL 的失败发生在产出向量之前。

改为 R2 数据源，直接喂 `dist/raw` 下的 Markdown 原文：跳过抓取与转换两个环节，
同时避免导航、页脚、侧边栏等模板噪音进入分块。

**收益**：减少链路中的 Workers AI 调用环节；内容纯度提高，等价字号下有效信息密度上升。
**代价**：需要在 CI 中增加一步把 `dist/raw` 同步到 R2；更换数据源类型需要重建实例
（`instanceId` 与 `type`、`source`、`embeddingModel` 在创建时固定，
变更会触发实例替换）。

### 5.4 层四：调度与重试策略调整

1. **分离职责**：把实例侧 `sync_interval` 调整为较大间隔（如 86400），
   由 GitHub Actions 统一编排；或反之保留实例自<｜hy_place▁holder▁no▁813｜>，工作流改为只做状态巡检。
   二者取其一，避免同一批文件被两套机制反复重排。
2. **错峰多轮**：把每天一次的全量触发改为每天 4–6 次、间隔均匀的小轮次。
   3040 是瞬时态，分散到多个时间点可提高命中空闲窗口的概率。
   公开仓库的 Actions 用量无月度限制，此项无成本。
3. **收敛判据**：同步脚本改为输出「向量数与预估块数的比值」而非仅输出累计计数，
   达到阈值即轮空本轮，避免无谓重排。

### 5.5 层五：付费杠杆

Workers Paid 计划月费 5 美元，仍包含每日 10,000 免费 Neurons，
超出部分按 $0.011 / 1,000 Neurons 计费（单次全量索引约 214 Neurons，折合不足 0.003 美元）。
其实际作用是提升容量队列优先级：Cloudflare 于 2026-07-28 起限制免费层访问部分资源密集型模型，
公开口径即为「减少 429 与 3040（Out of Capacity）错误」。

**收益**：直接针对瓶颈，见效最快。
**代价**：引入固定月支出。按当前用量估算（每日全量索引约 214 Neurons、
单次问答约 60 Neurons），月度用量远低于免费额度，超出计费部分可忽略，
实质支出即 5 美元月费。是否可接受属于维护取舍，不由技术因素单独决定。

### 5.6 层六：检索侧参数调优（虽列于末位，应最先执行）

前五层都在处理「索引建不全」。但空结果还有第二个成因，与索引进度正交：
`keyword_match_mode` 默认为 `and`，要求所有查询词都命中同一文档。
在索引覆盖不完整的前提下，多词查询会因此直接返回空。

2026-09-14 实测对照，命中数随查询词数增加而骤降：

| 查询 | 词数 | 命中 |
| --- | --- | --- |
| `Redis` | 1 | 3 |
| `Docker` | 1 | 5 |
| `安装` | 1 | 10 |
| `Redis 安装` | 2 | 1 |
| `Docker Redis` | 2 | 1 |
| `Docker 安装 Redis` | 3 | 0 |

单词查询均有结果，两词查询降到 1 条，三词查询为空，符合 and 模式的特征。
`Docker 安装` 仍返回 10 条，是因为同时含这两个词的文档在本站较多，
反证了过滤确实发生在「词项是否共现」这一层，而非语义层面。

| 参数 | 实例默认 | 建议值 | 是否触发重索引 |
| --- | --- | --- | --- |
| `retrieval_options.keyword_match_mode` | `and` | `or` | 否 |
| `score_threshold` | 0.4 | 0.2 | 否 |
| `context_expansion` | 0 | 1（实例级不支持，见下） | 否 |

**查询侧无法覆盖**：实测向 NLWeb 的 `/ask` 传入 `ai_search_options`、
`retrieval_options`、`keyword_match_mode`、`match_threshold` 均不改变返回结果，
该接口不透传检索参数，因此只能在实例级配置。

**收益**：三项均只影响查询期行为，不触发重索引、不改数据源、不影响已入库向量，
可随时改回。即使索引长期停在约 25% 覆盖，多词查询也能恢复召回。
**代价**：`or` 模式会引入仅含部分查询词的文档，排序依赖 BM25 相关性，
需配合 `score_threshold` 控制噪音上限。

执行脚本为 `scripts/cloudflare-ai-search-tune-retrieval.sh`，支持 `DRY_RUN=1` 先看变更对照。

#### 5.6.0 一项已排除的项

`context_expansion`（命中块向邻近块扩展 0–3 段）只在单次请求的
`ai_search_options.retrieval` 中生效。实例级写入返回 2xx 但被静默丢弃：
写入后回读，`retrieval_options` 仍只有 `keyword_match_mode`，顶层与嵌套两种写法结果一致。
§5.6 已确认 NLWeb 的 `/ask` 不透传检索参数，因此该能力当前无法启用，
脚本与实例配置均已移除该字段。

#### 5.6.1 一项收益有限的补充

`content_selector` 支持按 CSS 选择器限定每页的索引范围，站点可用
`[data-pagefind-body]` 或 `.sl-markdown-content` 命中正文容器。
按 40 个页面抽样，正文词数占整页去噪后的 88.9%，可削减噪音约 11%。
收益不高，且更新该字段会立即触发新同步作业，故不作为推荐项，
仅在需要一并削减模板噪音时考虑。

需注意该字段要求「选择器必须命中唯一元素，命中多个时忽略该选择器并回退整页」，
因此宜用 `[data-pagefind-body]` 这类唯一属性而非宽泛的容器类名。

## 6. 推荐顺序

层六虽列在末位，执行顺序上应排在最前：它不触发重索引、不改动数据源、
可随时回滚，且改善的是与索引进度无关的另一个成因。

| 序 | 动作 | 成本 | 预期效果 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 修正 `cloudflare/README.md` 与既有 ADR 中的归因与参数单位 | 无 | 决策依据不再失真 | 已完成 |
| 2 | 层六：检索侧调优（`or` + 阈值 0.2，`context_expansion` 已排除） | 无 | 多词查询恢复召回，不必等索引收敛 | 已完成（2026-09-15） |
| 3 | 增强同步脚本的错误分类与覆盖率输出 | 无 | 瓶颈是否转移可被观测 | 已完成 |
| 4 | 层四第 1、2 项：分离调度职责并改为错峰多轮 | 无 | 提高单轮成功率 | 待评估 |
| 5 | 层一：切换到 keyword-only + trigram 建立全量索引 | 无 | 覆盖率由约 25% 到接近 100% | 已触发（2026-09-15），待复验 |
| 6 | 复验关键词索引下的问答效果，据此决定是否启用层二 | 低 | 复合查询不再落空 | 待执行 |
| 7 | 层三：改为 R2 直喂 Markdown | 中 | 削减链路环节 | 待评估 |
| 8 | 层五：评估 Workers Paid | 5 美元/月 | 直接提升容量优先级 | 维护取舍 |
| 9 | 层一阶段 B：条件具备后切回 hybrid 补齐向量 | 低 | 恢复语义召回 | 待执行 |

第 2 项与第 5 项分别作用于两个独立成因，可并行推进而非替代关系：
第 2 项解决「有内容但取不回」，第 5 项解决「内容还没进去」。

第 5 项依赖第 1 项：若沿用「额度耗尽」的错误归因，
会误把精力继续放在压缩内容规模与调整触发时点上。

第 2 项与第 6 项的判据都应当量化：准备一组覆盖「命令名」「配置项」「跨主题组合」
的查询样本，在每次调整前后分别记录命中数与首位相关性，
据增益与噪音的对比决定是否继续推进层二。

## 6.1 决策记录（2026-09-15）

维护者选择层一（关键词单路）作为主攻方向，层二至层五暂缓。决策依据：

- 层一是零现金成本项中唯一能解除对嵌入产能依赖的一条，
  其余各层要么只降低请求量（收益上限约 40%）、要么引入固定支出或开发成本；
- 2026-09-15 03:05 UTC 的同步显示覆盖率仍为 0%（队列 207、失败 160，
  其中 159 条为 3040），继续沿用既有策略未见收敛趋势；

## 6.3 分词器字段位置错误与中文召回（2026-09-15）

| `主从复制` | 2 次 | 0 |

「集群部署」「主从复制」在正文中确有出现，且这些查询此前未被执行过，
可排除 §6.2 提出的缓存假设。回读实例配置后定位到根因：

```
indexing_options: {"keyword_tokenizer": "porter", "use_ocr": false}
```

`keyword_tokenizer` 一直被写在请求体顶层，接口静默丢弃，
实例始终使用默认的 `porter`（英文词级分词 + Porter 词干）。中文没有词间空格，
porter 无法切出有效词项，因此纯中文查询全部落空；英文与标识符不受影响。

处置：字段移入 `indexing_options` 并触发全量重索引；配置脚本增加写入后回读，
输出 `index_method`、`keyword_tokenizer`、`keyword_match_mode`、`score_threshold`，
使同类静默丢弃能在执行时暴露。

**教训**：该接口对未知字段不报错，只丢弃。涉及检索行为的每一项配置，
都必须在写入后回读确认，不能仅凭 HTTP 状态码判断生效。

> 2026-09-16 补充：中文召回的最终处置是把召回移到浏览器端的 Pagefind，生成由
> 自建 Worker 承担，见 `adr/2026-09-16-问答生成端的部署与生成链路.md`。

## 7. 待实测验证项

以下结论依据公开文档与既有观察推断，落地前需要逐项确认：

1. `keyword_match_mode: or` 与 `score_threshold: 0.2` 组合下的噪音增量。
   建议先准备一组查询样本（覆盖命令名、配置项、跨主题组合三类），
   分别在调整前后记录命中数与首位相关性，确认召回增益大于噪音代价。
   2026-09-15 补充：`or` 已启用，多词查询（`Nginx 配置`、`Docker Redis`、
   `Docker Compose 安装`）由空转为命中；阈值 0.2 与 0.1 的命中数无差异，
   噪音增量需换用更细分档继续观测；
2. keyword-only 模式（`index_method: {keyword: true, vector: false}`）下的索引作业
   是否确实不产生嵌入请求、且不受 3040 影响。
   2026-09-15 已验证：切换后失败由 160 降至 0，全量 367 篇入库，见 §6.2；
3. `keyword_tokenizer: trigram` 对中文技术文档的召回增益，与 `porter` 的对比。
   2026-09-15 补充：对比已在无意中完成——字段位置错误导致实际使用 porter 时，
   纯中文查询命中恒为 0；trigram 生效后的复验结果见 §6.3 后续记录；
4. `cache`、`cache_threshold`、`cache_ttl` 在查询侧的实际命中率，
   以及在索引未收敛时对空结果的掩盖程度；
5. 层二自建 Worker 在 Cloudflare Workers 运行时内能否直接消费 `/pagefind/**` 索引
   （Pagefind 运行时依赖 WASM 与自有索引格式），若不可行则改用 `/raw/**` 加轻量打分。
   2026-09-16 已回避该问题：召回改在浏览器端完成，Worker 只接收片段并生成答案，
   无需在 Workers 运行时内解析 Pagefind 索引，
   见 `adr/2026-09-16-问答生成端的部署与生成链路.md` §2；
6. 层三 R2 换轨后，Markdown 转换环节的节省量是否足以改变批量失败的结果。
