# 根路径跳转与首屏闪烁

## 1. 现象与实测

`https://doc-record.iuin888vip.icu`（不带语言前缀）会先显示一个空白页再跳到 `/zh-cn/`。
实测（Chromium，暗色系统主题，冷启动）：

| 时刻 | 状态 |
| --- | --- |
| 80ms | URL 仍是 `/`，`body` 背景透明（暗色主题下即白屏），页面文字是 “Redirecting from / to /zh-cn/”，标题 `Redirecting to: /zh-cn/` |
| 200ms | 已在 `/zh-cn/`，背景为主题深色 |
| 342–719ms | 另一轮测量：`commit` 在 342ms，落到 `/zh-cn/` 在 719ms |

同时确认首屏**字体**不是问题：三个 Geist woff2 都已 `rel=preload`，主题自带公制匹配回退
（`size-adjust` / `ascent-override`）且用 `font-display: swap`，属当前最佳实践，本次未改。

## 2. SEO 现状评估

被跳转的根路径本身**不会**伤害 SEO，Astro 生成的存根已带正确信号，实测：

- 根路径返回 200 + `<meta http-equiv="refresh" content="0;url=/zh-cn/">`：Google 把 0 秒
  meta refresh 视为永久跳转；
- `noindex` + `canonical` → `/zh-cn/` 两者都在，避免与首页形成重复内容；
- 根路径**不在** sitemap（`sitemap-0.xml` 只有 `/zh-cn/...`），robots.txt 也不特殊处理；
- 首页自身 `canonical` 指向 `/zh-cn/`（自指，正确）。

真正的短板有三处：

1. **分享预览**：存根没有任何 `og:*`，标题是 `Redirecting to: /zh-cn/` —— 而人分享的恰恰是
   裸域名，聊天工具/社交平台只会抓到一个空壳；
2. **多一次往返**：入口 URL 需要 300–700ms 的额外跳转，移动网络下更明显，且伴随白屏闪烁；
3. **200 而非 301**：语义上是软跳转，不解析 meta refresh 的客户端（部分抓取器、链接预览、
   无 JS 环境）只能停在存根页。

## 3. 决策（已实施）

**3.1 用自定义存根取代框架默认存根**（`src/pages/index.astro`，并从
`astro.config.mjs` 移除 `redirects['/']`）：

- `<head>` 内联 `location.replace('/zh-cn/')`：在解析 body 之前跳转，通常早于首次绘制，
  用户不再看到中间页；
- 保留 `meta refresh` 作为无 JS 与纯 HTML 抓取的兜底（语义与 301 存根等价）；
- `noindex` + `canonical` 保持不变；
- **补齐 `og:*` / `twitter:*`**，`og:url` 指向 `/zh-cn/`，使裸域名的分享预览显示真实站点信息；
- 背景用 CSS 系统色 `canvas`（配 `color-scheme: light dark`）：亮暗主题各自成立，不再白屏，
  也无需复制主题配色变量。

**3.2 站点常量收敛为单一来源**（`src/lib/site.ts`）：`DEFAULT_LOCALE`、`SITE_TITLE`、
`SITE_DESCRIPTION` 由 `astro.config.mjs`、根路径存根、`src/lib/category.ts` 共同引用。
这同时解决了代码审查发现项 L5（默认语言标识在配置与分类页各写一份的漂移风险），
故在 `adr/2026-10-14-代码审查发现项处置.md` 中将 L5 标记为已解决。

## 4. 备选方案与取舍

| 方案 | 收益 | 代价 / 风险 | 结论 |
| --- | --- | --- | --- |
| **本次实施**：自定义存根 | 消除白闪与可见中间页、补齐分享元信息，零基础设施改动 | 仍是 200 软跳转；跳转依赖客户端 | 已实施 |
| **Cloudflare 边缘 301**：域名走 CF 代理 + Redirect Rule `/` → `/zh-cn/` | 对所有客户端都是标准 301，零额外往返，无存根 | 需改 DNS/代理；GitHub Pages 的证书签发与续期依赖 HTTP-01 验证，套上 CF 代理后可能失败（需 Full/Strict 与验证路径放行）；引入 CF 缓存层需复核缓存规则 | 建议单独立项评估，不在本次改 |
| **迁到 Cloudflare Pages** | `_redirects` 原生 301、边缘缓存、预览部署；与既有 Workers / AI Search 同侧 | 需重写部署链路与域名/证书迁移，并在迁移后全量复验 | 战略级，另立 ADR |
| **默认语言改回 root locale** | `/` 直接是中文首页，零跳转 | 等于回退 2026-09-11 的既有决策（§13.4：让内容结构符合 Starlight 语言目录约定），并要重做全站 URL、canonical、sitemap 与 AI Search 排除规则 | 明确不做 |
| **字体改 `font-display: optional`** | 首访也不发生换字 | 放弃排版一致性（首访用系统字体） | 未做，属排版取舍，需另行拍板 |

## 5. 验证

- 产物断言：`dist/index.html` 含内联 `canvas` 背景、`noindex`、`canonical`、`og:title`、
  `og:url`、`meta refresh` 兜底与 `location.replace`，且不再出现 `Redirecting` 文案；
- e2e：新增用例「根路径给出 canonical/noindex/og，并跳转到默认语言首页」，无 JS 用
  `request.get('/')` 校验真实 HTML，浏览器端断言最终落到 `/zh-cn/`；
- 线上复测：部署后重跑同一套时序截图，80ms 处不应再是白屏（见提交说明中的实测记录）。

## 6. 决策前补充实测（2026-10-14，供边缘 301 与字体两项决策）

存根改造上线后重新测了一轮，用于判断"是否值得动基础设施"：

| 指标 | 实测 | 含义 |
| --- | --- | --- |
| 存根 TTFB | 63–196ms（冷启动首击 451ms） | 真 301 能省下的就是这一次文档往返 |
| 存根 HTML 体积 | 1.5 KB | 与往返时延相比可忽略 |
| `/_astro/*` 缓存头 | `cache-control: max-age=600` + ETag（304 生效） | 内容哈希资源本可 `immutable`，GitHub Pages 不支持自定义响应头 |
| 单页静态资源 | 7 JS + 3 CSS + 3 woff2 | 10 分钟后回访会产生十余次条件请求 |
| 换字位移（CLS，冷启动） | `/zh-cn/` 0.0000（0 次位移）、文档页 0.0027（1 次） | 主题自带公制匹配回退，换字不产生可见位移 |
| `document.fonts.ready` | 1379ms / 939ms（均晚于 FCP） | 换字确实发生，但影响可忽略 |

由此得到三条结论，供后续决策：

1. **边缘 301（Cloudflare 代理 + Redirect Rule）不建议做**：存根改造后，它剩下的收益只是
   一次往返（60–200ms）与 HTTP 语义；代价是把 CF 代理架在 GitHub Pages 前，GitHub 侧
   Let's Encrypt 的 HTTP-01 续期可能拿不到验证请求（90 天周期的定时故障），要么周期性
   手工切回 DNS-only，要么降低 SSL 模式 —— 收益与风险不成比例。
2. **迁 Cloudflare Pages 值得单独立项**，但理由排序不是 301：
   ① `_headers` 可控响应头（`/_astro/*` 改 `immutable` + 安全头，GitHub Pages 完全做不到）；
   ② 每个 PR 的预览部署（与既有 e2e/typecheck 门禁配套）；
   ③ 证书由 CF 托管，不再有 HTTP-01 续期问题；④ 真 301 与存根消失，只是顺带。
   代价：部署链改写（`wrangler pages deploy` 或 CF Git 集成）、域名与 DNS 切换、复验
   sitemap/robots/raw/llms/RSS 与全套 e2e、保留 GitHub Pages 项目作为回滚路径。

   配额核实（2026-10-14；来源：Cloudflare Pages Limits `Last updated Sep 5, 2026`、
   Pages Functions Pricing `Sep 8, 2026`、GitHub Pages limits 文档）：

   | 项 | Cloudflare Pages 免费额度 | 本站现状 |
   | --- | --- | --- |
   | 静态资源请求 / 带宽 | **免费且不限量**（免费与付费一致） | — |
   | 站点文件数 | 20,000 | 2,025 |
   | 单文件体积 | 25 MiB | 1.39 MiB |
   | 构建次数 | 500/月、1 并发（Git 集成，超时 20 分钟） | 近 30 天 38 次推送 |
   | 项目数 | 100/账号（不常规上调） | 1 |
   | 自定义域名 | 100/项目 | 1 |
   | `_redirects` / `_headers` | 2,100 条 / 100 条 | 1 条 / 约 5 条 |
   | 预览部署 | 不限量 | — |
   | 备注 | 新账号前 48 小时创建项目有节流；Pages Functions 请求占用 Workers 免费额度（100k/天），本站不需要 Functions | — |

   对照：GitHub Pages 现行文档为「发布站点不超过 1 GB、带宽软上限 100 GB/月、部署 10 分钟
   超时」，本站产物 258 MB（约 26%），长期看这是更早会遇到的那条线。
3. **字体的 `font-display` 不改**：`optional` 解决的是测不到的位移（CLS 已为 0.0000/0.0027），
   代价是首访放弃 Geist；而 Geist 子集只覆盖拉丁字符，中文一直由系统字体渲染，
   换字可见面本来就很小。

## 7. 迁移目标的修正与市场核实（2026-10-16）

第 6 节把迁移目标写成 Cloudflare Pages，核实后需要修正：**Cloudflare 已把新项目指向 Workers**。

- Pages 文档首页原文：「Are you sure you want to use Pages? Workers supports most Pages use
  cases and offers a broader feature set. It is Cloudflare's primary platform for building
  applications. **Start new projects with Workers.**」Pages 仍在维护（Limits 文档 2026-09-05
  更新），但已不是新项目的推荐落点；官方另有「Migrate from Pages to Workers」指引（2026-10-12）。
- Workers 静态资源（Static Assets）具备迁移所需的全部能力：`_headers` 与 `_redirects`
  原生支持（用法与 Pages 一致），**静态资源请求免费且不限量**；与本项目相关的 Pages 免费额度
  （文件数 20,000、单文件 25 MiB、构建 500/月、项目 100/账号、预览部署不限量）在 Workers 侧
  同样不构成约束。两点注意：脚本按请求执行时占 Workers 免费额度 100k/天（纯静态站不触发）；
  开启 Workers Caching 后命中缓存的请求也按请求计费，静态站无需开启。
- **迁移成本比原估计低**：本站域名 `iuin888vip.icu` 的权威 NS 已是
  `junade/mckinley.ns.cloudflare.com`，`doc-record` 记录为 DNS-only 直指 GitHub Pages
  （带 CNAME 扁平化特征）—— zone 已在 Cloudflare，接自定义域名不需要迁移 NS。

市场核实（用于判断"是不是主流"）：

| 证据 | 结果 |
| --- | --- |
| 官方是否提供该迁移路径 | 有专门教程「Migrating a Jekyll-based site from GitHub Pages」（2026-04-21 更新），另有自 Netlify、Firebase 的迁移指南 |
| 实际案例 | GitHub 上标题含「GitHub Pages to Cloudflare Pages」的 issue/PR 约 89 条（100 条取样上限内），多为个人站与文档站，与本站同类 |
| 生态位次 | Astro 官方部署指南同时列出 GitHub Pages、Netlify、Vercel 与 Cloudflare（含专用图标），属一等部署目标 |
| 体量对比（Stack Overflow 标签） | `github-pages` 4,961 问 vs `cloudflare-pages` 113 问；`netlify` 2,198、`vercel` 3,295（标签量反映疑难量级与平台年龄，不等于站点数） |

结论：这是**有官方路径、有成规模先例的常见迁移，但不是默认主流**——GitHub Pages 仍是仓库型
文档站的零摩擦默认选择，需要响应头/重定向/预览部署时才转向 Netlify、Vercel、Cloudflare 三家。
因此"随大流"或"吃螃蟹"都不构成理由；决策仍应回到收益本身（可控响应头、预览部署、摆脱 1 GB
与无重定向限制）与长期性（Workers 是官方主平台）。若立项，目标应是 **Workers 静态资源**，
不是 Pages。

### 7.1 与既有 Cloudflare 资源的关系（不冲突）

常见疑问是"Workers 是不是只能有一个""会不会和 AI 检索抢资源"。按官方额度与本仓库
`cloudflare/README.md` 记录的既有资源核对，三条都不会撞：

| 维度 | 事实 | 结论 |
| --- | --- | --- |
| 数量 | Workers 免费额度为 **100 个/账号**（付费 500）；本账号现有两个：NLWeb `bold-union-4896-nlweb` 与生成端 `doc-record-ai-answer` | 站点再加一个为第 3 个 |
| "AI 索引"是什么 | 索引是 **Cloudflare AI Search 的托管实例** `bold-union-4896`（经 API/MCP 调用），不是 Worker；跑代码的是上述两个 Worker | 概念不同，不占 Worker 数量 |
| 额度 | 免费账号每天 10 万次**脚本调用**（账号级共享）；静态资源请求免费且不限量、不触发脚本 | 站点流量不占脚本额度；问答调用量极小；Workers AI 与 AI Search 额度是另外的维度。注意不要开 Workers Caching（命中缓存也按请求计费），静态站无需开启 |
| 主机名 | 现有两个 Worker 均在 `iuinin666.workers.dev` 子域 | 站点使用 `doc-record.iuin888vip.icu`，无冲突；zone 已托管在 Cloudflare，接自定义域名不需要迁移 NS |
| AI Search 抓取 | 抓取源是 URL（`https://doc-record.iuin888vip.icu/sitemap-ai.xml`）而非托管方 | 换托管方对爬虫透明，**不需要重建索引**（README §3.2 的"更换内容源需重建"针对 URL 集合变化） |

另一个设计选择是"合并进同一个 Worker"（既服务静态资源又提供 `/ask`）：技术上可行，但不建议——
生成端是"改代码才部署"、站点是"每次提交内容都要部署"，部署节奏与故障域不同，分开更干净，
而多一个 Worker 在免费额度内没有额外成本。



### 7.2 计费贴身问题与可用护栏（2026-10-16 核实）

常见顾虑是"站点与 AI 计费同处一个账号，会不会被流量带出账单"。核对后的事实是：
**迁移本身不增加计费暴露，真正的风险面是既有的公开 AI 端点**，且最硬的一层护栏是免费计划本身。

风险量化（用本站实际使用的 `@cf/qwen/qwen3-30b-a3b-fp8`）：

| 项 | 数值 | 来源 |
| --- | --- | --- |
| 模型单价 | 输入 4,625 neurons/百万 token、输出 30,475 neurons/百万 token（$0.051 / $0.335 每百万 token） | Workers AI Pricing |
| 单次问答成本（按本站上限：6 片段×1500 字 + max_tokens 800） | 约 30–70 neurons | 由上式推算 |
| 免费额度 | 10,000 neurons/天，超出**直接报错**（不产生费用） | Workers AI Pricing |
| 付费下 | $0.011/1,000 neurons 超出部分 ≈ $0.0008/次；被刷 10 万次约 $77 | Workers AI Pricing |

护栏分三层：

1. **平台硬约束（免费计划即具备，这就是"安全措施"）**：Workers 账号级 10 万请求/天，超出返回
   **Error 1027**；Workers AI 超出 10,000 neurons/天直接报错；**静态资源请求免费且不限量**，
   站点流量本身不产生费用。
2. **免费计划可配的主动防护**：Rate limiting 规则（免费计划 **1 条**，按 IP 计数，字段支持
   Path 与 Verified Bot，应花在生成端 POST 上）；**Turnstile**（免费计划可用，免 CAPTCHA
   人机验证）；WAF 托管规则与通知告警。应用层已有：CORS 白名单（**仅约束浏览器，不是访问
   控制**，与审查发现项 M4 同源）、片段归属 origin 相等校验（M2 修复）、请求体上限（M3）、
   contexts ≤ 6、单片段 1500 字、max_tokens 800 —— 单次请求成本因此被钉死。
3. **升级到 Paid 之后必须自己搭的**：平台**没有硬性支出上限**，只有
   [Budget alerts](https://developers.cloudflare.com/billing/manage/budget-alerts/)
   阈值邮件告警（仅 Pay-as-you-go 账户可用）。届时限流 + Turnstile + 预算告警三者缺一不可。

两条与迁移直接相关的硬性约束（写入实施清单作为验收项）：

- 站点 Worker 保持**零请求逻辑**（纯静态资源）：否则站点流量会消耗账号级共享的 10 万/天脚本
  调用额度，极端情况下会连累 AI 端点；
- **不要开启 Workers Caching**：命中缓存的请求按请求计费，静态站无需该能力。

隔离选项：把静态站点放到独立 Cloudflare 账号可让额度与账单完全隔离，代价是两套令牌与运维面。
当前不必——站点零计费面；若将来站点 Worker 需要跑逻辑（SSR、中间件），再评估隔离。

**实施决策（2026-10-16）：上述第二、三层一律不实施。** 本站处于 Workers Free 计划（见
`cloudflare/README.md` 记录的额度与升级取舍），滥用的最坏结果是当日免费额度耗尽、AI 端点当天
不可用（次日 00:00 UTC 重置），**不产生任何费用**；而 Turnstile 会给问答面板增加前端摩擦、
限流规则会新增一处需要维护的配置，收益与成本不成比例。仅在下列触发条件出现时重新评估：

1. 升级到 Workers Paid —— 届时先建一条 Budget alert 即可，其余仍非必要；
2. 出现真实滥用迹象：免费额度被异常耗尽，或日志里出现非本站来源的高频调用；
3. 这些端点因其他原因需要做访问控制时。

与迁移相关的两条"零逻辑 / 不开 Workers Caching"约束保留：它们不是要实施的措施，只是
**不要打开某个开关**，零成本。
