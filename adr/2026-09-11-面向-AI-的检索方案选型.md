# 面向 AI 的检索方案选型

## 1. 背景

站点已完成面向 AI 的基础输出：`llms.txt` 与按分类的分卷、`/raw/` 原文端点、
页面上的复制与跳转入口。这些能力解决的是「AI 能读到内容」，但解决不了
「读者用自然语言提问时能直接得到答案」——站内搜索仍是 Pagefind 的关键词匹配，
对「怎么给容器固定 IP」这类问法效果有限。

2026-09-11 对 Cloudflare 账户做了探查，发现既有资源：

| 资源 | 状态 |
| --- | --- |
| DNS 区域 `iuin888vip.icu` | 已托管 |
| NLWeb Worker `bold-union-4896-nlweb` | 在线，自带聊天界面、`/ask` 接口与 MCP 支持 |
| AI Search 实例 `bold-union-4896` | 存在，由 NLWeb 的 `RAG_ID` 绑定关联，**索引为空** |
| Workers AI 免费额度 | 每日 10,000 neurons，探查时已耗尽 |

实测 `/ask` 能正常响应但返回 `results: []`，即链路本身可用，缺的是内容。

## 2. 决策

**复用既有的 NLWeb + AI Search 实例，不自建向量检索链路。**

即：为 AI Search 实例配置以站点 sitemap 为入口的网页爬虫数据源，触发同步建立索引，
由 NLWeb 提供问答界面与 MCP 接口。

> **2026-09-16 修订**：中文问答的生成端与召回位置已调整。改为浏览器端 Pagefind
> 召回片段、提交给自建 Worker 生成答案，NLWeb 退为未配置生成端时的回退。
> 原因是 AI Search 的关键词索引对中文无召回（`trigram` 同样无效），且 NLWeb 的
> `/ask` 会在检索层有结果时把含中文的查询过滤为空。
> 「不自建向量检索链路」这一条不变 —— 召回改用站点构建产物中已有的 Pagefind 索引。
> 决策过程与实测结果见 `adr/2026-09-16-问答生成端的部署与生成链路.md`。

## 3. 方案对比

| 维度 | 复用 NLWeb + AI Search | 自建 Worker + 向量库 |
| --- | --- | --- |
| 既有投入 | 实例已部署，仅需灌数据 | 从零开发索引与检索逻辑 |
| 权限要求 | AI Search:Edit / Run | Vectorize:Edit、Workers AI、R2 |
| 维护内容 | 数据源配置与同步任务 | 分块、向量化、检索、重排、缓存全部自维护 |
| MCP 支持 | NLWeb 原生提供 | 需自行实现 |
| 可控性 | 受产品能力约束 | 完全可控 |
| 额外成本 | 无开发成本 | 开发时间长，且同样受 Workers AI 额度约束 |

自建方案的唯一优势是可控性，而当前需求（技术文档问答）并不存在
AI Search 无法满足的特殊要求，因此该优势不足以抵消开发成本。

## 4. 配置要点

- 数据源类型为 `web-crawler`，URL 发现方式为 `sitemap`，指向 `sitemap-ai.xml`；
- 向量模型为 `@cf/qwen/qwen3-embedding-0.6b`，生成模型为 `@cf/qwen/qwen3-30b-a3b-fp8`；
- 采用关键词与向量双路索引，混合检索对命令名与配置项更友好；
- 关闭重排与查询改写，减少每次调用的模型开销；
- 排除 `/raw/**` 与 `/_llms-txt/**`（与页面重复的纯文本副本）。

### 4.1 为什么用独立的 `sitemap-ai.xml`

选型当时 `sitemap-index.xml` 指向的 `sitemap-0.xml` 含 1492 条 URL，其中约四分之三是
`/en`、`/ja`、`/zh-Hant` 前缀的回退副本，正文与根语言页面一致。全量索引会放大
约四倍的向量写入量，且 `max_num_results` 的返回名额被近义重复块占满。

因此新增 `src/pages/sitemap-ai.xml.ts`，只输出根语言条目，构建产物 367 条 URL。
实例侧当时同时保留 `/en/**`、`/ja/**`、`/zh-Hant/**` 排除项作为兜底。

> 2026-09-11 变更：内容迁入 `src/content/docs/zh-cn/` 后，`locales` 只声明已有
> 译文目录的语言，回退副本不再生成，`sitemap-0.xml` 与 `sitemap-ai.xml` 的条目数
> 已收敛到同一量级（约 373 条）。语言前缀的排除项随之移除，`exclude_items` 现为
> `/raw/**` 与 `/_llms-txt/**`。新增语言且译文不全时，需在排除项中补回对应前缀。

实测确认：触发同步后队列按 `sitemap-ai.xml` 重建为 360 条，即新站点地图已生效；
修改 `specific_sitemaps` 不会重置进行中的队列，需要靠一次新同步任务重建。
URL 结构整体变化时连同步任务也不足以清除失效条目，需删除实例后重建，
入口见 `cloudflare/README.md` §3.2。

配置脚本为 `scripts/cloudflare-ai-search-setup.sh`，步骤见 `cloudflare/README.md`。

## 5. 约束与风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Workers AI 嵌入侧容量不足（3040） | 索引作业批量失败，覆盖率长期停滞在约 25% | 错峰多轮；先以关键词单路建立全量覆盖；升级 Workers Paid 提升优先级 |
| Workers AI 当日额度耗尽（3036） | 当日无法继续索引与问答，次日 00:00 UTC 自动恢复 | 控制重跑次数；区分两类错误后再决定是否重试 |
| API 令牌权限不足 | 无法配置实例 | 创建仅含 AI Search:Edit 与 AI Search:Run 的专用令牌 |
| 译文目录被排除 | 目标语言问答检索不到译文 | 译文上线后从排除项中移除并重新同步 |
| 站点结构变化导致索引陈旧 | 答案指向不存在的页面 | 每日同步一次，必要时手动触发 |

### 5.1 额度与容量实测结论

> 本节第一段的判读已于 2026-09-14 更正，修订后的结论见
> `adr/2026-09-14-AI-Search-容量限流调优.md` §2。

2026-09-11 08:30 UTC 直接调用嵌入模型，返回
`you have used up your daily free allocation of 10,000 neurons`，
说明当天确实发生额度耗尽（错误码 3036）。同期索引任务报
`workers_ai_out_of_capacity_error` 属另一类错误（错误码 3040，瞬时容量不足），
当时的记录把后者归因于前者，该归因不成立：两者均返回 HTTP 429 但性质相反，
3036 重试无效而 3040 重试通常成功。

按官方单价（嵌入模型 1075 neurons / M input tokens）估算：

- 根语言文档 368 篇，合计约 49.7 万字符，折合约 0.20 M token；
- 单次全量索引约 214 neurons，占每日免费额度的 2%；
- 单次问答（8 段上下文加 800 token 输出）约 60 neurons。

结论是**免费额度足以支撑日常索引与问答**：全量索引约占每日额度 2%，
即使每日重跑十次也仅约 20%。当天额度被耗尽的原因是此前的失控爬取：
1492 条 URL 叠加实例的反复重建与重试。

需要区分的是「额度是否够用」与「容量是否可用」。额度够用已于此证实；
而 2026-09-13 至 2026-09-14 的连续两次同步均在额度重置后不久触发、
且失败明细全部为 3040，说明彼时的瓶颈是免费层在嵌入高峰期的容量优先级，
与额度无关。因此「不必升级 Workers Paid」这一结论所依据的理由已经失效，
是否升级应改由「是否需要提升容量队列优先级」来决定，详见
`adr/2026-09-14-AI-Search-容量限流调优.md` §5.5。

## 6. 与既有 AI 能力的关系

本方案与已有的 `llms.txt` 是互补而非替代关系：

- `llms.txt` 面向「把整站交给外部大模型」的场景，一次性提供全量上下文；
- AI Search 面向「读者在站内提问」的场景，按相关性取回片段再生成答案。

两者共用同一份内容来源，无需重复维护。

## 7. 页面接入

问答检索的是全站索引，与「复制 Markdown / 跳转 ChatGPT / Claude」这类只作用于
当前文档的操作不同源。2026-09-17 起两者拆分：

- 标题区的文档级操作由 Black 主题的 MarkdownActions 承载（复制整页、
  在 ChatGPT / Claude / v0 / Scira 中打开），自研的 AiActions 已移除；
- `src/components/AiAsk.astro` 承载问答，做成了全局悬浮入口（右下角），
  经 `PageFrame.astro` 覆盖挂到每个页面 —— 首页与博客列表等无标题区的页面
  也有入口。面板明示「检索范围为全站文档」，避免被理解为问当前文档。

问答面板按构建期环境变量选择链路：

- 配置了 `PUBLIC_AI_ANSWER_URL` 时，由浏览器端 Pagefind 召回片段，提交给自建
  生成端生成答案（2026-09-16 起采用）；
- 未配置时回退到 NLWeb `/ask`，解析其 SSE 流渲染答案与来源链接。NLWeb 已开放
  跨域（`access-control-allow-origin: *`），因此无需自建代理，端点地址可用
  `PUBLIC_NLWEB_ASK_URL` 覆盖。

`PUBLIC_AI_ANSWER_URL` 已在 `.github/workflows/ci.yml` 的构建步骤中注入。
生成端的部署路径、生成改为非流式的原因与实测结果，见
`adr/2026-09-16-问答生成端的部署与生成链路.md`。

面板文案沿用 Starlight 的 i18n 机制，已补齐中、英、日、繁体四种语言。
