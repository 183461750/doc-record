# 博客条目退出文档侧边栏

## 1. 现象

博客文章页底部同时出现两套上下篇导航，且两套给出的邻居互相矛盾：

| 位置 | 渲染者 | 邻居取值 |
| --- | --- | --- |
| 正文末尾的卡片（`.sl-blog-pagination`） | starlight-blog 的 `PrevNextLinks` | 按 `date` 降序，`date` 相同则按标题 |
| 「编辑此页」下方的横条（`.pagination-links`） | Starlight 的文档 `Pagination` | 按 docs 侧边栏的目录字母序 |

以 `/zh-cn/blog/docker/dev_utls/dev-container/remote-ssh/cpolar/article/doc/` 为例：
卡片给出「frp…sshuttle / docker-compose…」，横条给出「Mihomo… / frp…clash」。

同时，14 篇博客文章以 `blog` 分组平铺在**文档**侧边栏里（普通文档页可见）。

## 2. 根因

1. `starlight-blog` 强制博客文章放进 docs 集合（本站 `src/content.config.ts` 以
   `docsSchema({ extend: blogSchema })` 承载），因此每篇文章都是一个普通 docs 条目；
2. 本站未声明 `sidebar`，Starlight 对整棵内容树 `autogenerate`，`zh-cn/blog/**`
   自然成为文档侧边栏的一个分组；
3. Starlight 的页脚无条件渲染 `<Pagination />`（`@astrojs/starlight/dist/components/Footer.astro`），
   其 `pagination` 在路由数据生成时按 **docs 侧边栏**扁平化取「当前项 ±1」
   （`dist/utils/routing/data.js` → `getPrevNextLinks`）。插件中间件随后只把
   `sidebar` 换成博客侧边栏，从不重算 `pagination`，也不覆写 `Footer`/`Pagination`
   （它只覆写 `MarkdownContent`，开启页头导航时再覆写 `SiteTitle`/`ThemeSelect`）；
4. 插件自身的设计并非如此：它为文档侧边栏注入**唯一一条** `Blog` 入口
   （`sl-blog-mobile-link`，指向 `/zh-cn/blog/`），文章列表归博客页自己的侧边栏。
   本站的 `autogenerate` 把 14 篇文章一并吸收，于是它们既污染文档信息架构，
   又成为文档分页的邻居。

上游状态：`starlight-blog` 0.30.0（当前最新）仍无 `Footer`/`Pagination` 覆写，
问题未被上游处理；其内置文案也只有 `en`/`fr`/`it`/`de` 四种语言。

## 3. 决策

在 `src/content.config.ts` 的自定义 loader 中，把 `<语言目录>/blog/**` 的条目
统一置为 `sidebar.hidden`（与既有的 `title` 推导同处一地，作者无需逐篇声明）。
效果：

- 文档侧边栏只保留插件注入的 `Blog` 入口，文档信息架构恢复纯文档；
- 文档分页在博客页找不到当前项 → `prev`/`next` 均为 `undefined`，重复导航消失；
- 文档页自身的上下篇不受影响：隐藏条目直接从侧边栏树中剔除，不会留下断链。

## 4. 备选方案（未采用）

| 方案 | 放弃原因 |
| --- | --- |
| 覆写 `Pagination` 组件，博客页返回 `null` | 只治症状：文档侧边栏仍平铺 14 篇博客；且要在站点侧重复实现插件的「是否博客页」判定 |
| 逐篇 front matter 写 `prev: false`/`next: false` | 14 篇以及以后每篇都要写，与本站「作者不必声明 front matter」的取向冲突 |
| 手工声明 `sidebar`，逐目录列举 `items` | Starlight 的 `autogenerate` 不支持排除子目录，只能改为手工列举全部一级目录，维护成本高于收益 |
| 等上游修复 | 0.30.0 未处理；且博客本就不属于文档 IA，上游即使补上「博客页不渲染文档分页」，本决策依然成立、无需回退 |

## 5. 顺带修正

- **日期回填**：14 篇中 8 篇 `date` 同为 `2024-05-22`，插件在 `date` 相同的组内
  退化为按标题排序，上下篇顺序因此没有实际意义。按《2026-09-11-Astro-Starlight-迁移实施记录》
  §5.5 已确立的规则（文件首次提交的 git 作者时间）回填这 8 篇；回填后 14 篇的
  `date` 与 `git log --follow --diff-filter=A --format=%ad --date=short` 逐条一致。
- **插件文案缺中文**：`starlight-blog` 不内置 `zh-CN`，博客页会渲染出
  `starlightBlog.post.date`（日期位置直接显示键名）、`starlightBlog.sidebar.*`、
  `starlightBlog.tags.count` 等原始键。按 Starlight 的覆盖机制在
  `src/content/i18n/zh-CN.json` 补齐全套键（用户译文优先于插件译文）。
  `en.json` 无需同步（插件自带英文）；`ja.json`、`zh-TW.json` 不预先补译文：
  Starlight 的文案查询基于 i18next 且 `fallbackLng` 指向默认语言，缺键会回退到
  `zh-CN` 的取值，不会渲染出原始键，等这两种语言真正进入 `locales` 时再按译文补齐。
- **类型门禁归零**：`pnpm check` 原有 4 条历史错误，与本次改动无关但阻塞门禁——
  `src/plugins/remark-strip-duplicate-h1.ts` 直接 `import type ... from 'mdast'`，
  而 `@types/mdast` 只存在于依赖树里（pnpm 严格布局下不可解析），连带 `node.children`
  的回调参数成为隐式 `any`；分类索引页对 schema 里可选的 `title` 直接调用
  `localeCompare`。已把 `@types/mdast` 声明为直接 devDependency（沿用依赖树中的
  4.0.4，仅 +3 行锁文件），分类索引页补 `?? doc.id` 兜底。现基线为 0 错误，
  并新增 `.github/workflows/typecheck.yml` 作为 PR 门禁。
  期间实测到一条框架约束：`title` 在 schema 中**必须**保持可选，因为 Astro 在
  `docsLoader` 内部（glob loader 的 `getEntryData`）就按 schema 校验 front matter，
  早于本站 loader 的标题补齐；改为必填会让全部未写 front matter 的文档构建失败。

## 6. 验证

- 构建产物核对（`pnpm build` 后直接读 `dist/`）：
  - 文档页侧边栏的 `/zh-cn/blog/` 链接由 15 条降为 1 条（插件入口）；
  - 博客文章页 `.pagination-links` 内链接数为 0，`.sl-blog-pagination` 内为 2；
  - 文档页文档分页仍为 2 条，未受影响；
  - 插件文案不再出现原始键（`grep -rho 'starlightBlog\.[a-zA-Z._]*' dist --include='*.html'`
    无输出），日期按 locale 渲染为 `2025年12月7日`。
- e2e 回归：`tests/e2e/site.spec.ts` 新增
  「博客文章页只有一套上下篇导航」与「文档侧边栏只保留唯一的博客入口，不列出博客文章」
  两例，随 `pnpm test:e2e` 与 `.github/workflows/e2e.yml` 运行（16 passed）。
- 类型门禁：`pnpm check` 由 4 条历史错误降为 0，由 `.github/workflows/typecheck.yml` 守门。
- 耦合提示：loader 中的 `BLOG_DIRECTORY` 与 starlight-blog 的默认 `prefix`（`blog`）
  以及「`entry.id` 首段是语言目录」的约定耦合，改动其中任一项需同步；e2e 用例充当哨兵。
